## 模块一 · Q1：first token 从 5–10 秒稳定压到 2 秒

**结论**：先砍掉不该进 context 的东西，再谈加速。应用层能做的做完，2 秒基本就到位了，不需要动推理栈。

**做法**

1. **固定前缀吃 prompt cache。** system prompt 和工具 schema 每轮都一样，必须放最前面，且序列化结果字节级稳定。命中缓存后这部分几乎不计入首 token 开销。工具 schema 是每轮从 registry 现生成的，所以注册顺序要固定——顺序一变，缓存全废。
2. **输入侧分流。** 多模态不把原图塞 prompt，先异步跑 OCR / 描述，prompt 里只放文本摘要，原图走引用。长文档同理，首轮只带命中的片段，不整篇塞。
3. **动态裁上下文。** 工具超过 10 个就按意图分组，只挂当前需要的；历史只带最近若干条加一条摘要，不再无脑全量。
4. **兜底交给 UX，不交给模型。** 缓存没命中时先流式吐一个占位首字，把用户感知的等待截断在几百毫秒内，剩下的时间等真结果。

**取舍**：投机解码、蒸馏小模型、分块预填我不放第一步。这些是改推理栈，成本和上线周期都高，收益还不稳定；而上面 1、2 两项在应用层当天能上线。首 token 慢，大头往往是"不该进 prompt 的东西进了 prompt"，不是模型本身慢。

**当前项目落点**：mini-agent 每轮全量发 system 加 4 个工具 schema，还没做缓存——4 个工具体量很小，加了也测不出差别。上生产的顺序是先做 schema 字节稳定和缓存，再做工具分组加载。

## 模块二 · Q1：和 Agent 熟悉半个月后，用户问了以前问过的问题，怎么召回

**结论**：召回的关键不是"查得到"，是"答得和上次一致"。查到一段相关记忆却给出相反答案，比不召回更糟。

**做法**

1. **写入侧存结构化记忆，不存原文。** 每条记忆是「用户问题 + 当时的结论 + 关键实体 + 时间戳 + 来源 session」。原文丢了没关系，结论和实体必须在，否则召回回来只是一堆没用的对话。
2. **双路检索。** 向量负责语义相近（用户换个说法也能命中），关键词 / BM25 负责专有名词和项目名。像 Chroma、Spring AI 这类词向量经常飘，关键词反而准。两路结果做 RRF 融合再取 top-k。
3. **召回时机让模型决定。** 把 memory_search 做成一个工具，description 写清"涉及用户历史偏好、之前问过的问题、跨会话事实时调用"。不要每轮硬塞 top-3——大部分轮次根本不需要历史，硬塞只会污染当前上下文。
4. **命中后的处理才是重点。** 注入时写成"用户 X 天前问过类似问题，当时的回答是……"，并加一句约束：如果当前判断和上次不同，必须说明差异原因，不要直接给矛盾结论。

**取舍**：不做全自动每轮召回。一是 token 成本，二是模型会把旧结论硬套到新问题上，反而更容易答错。显式工具召回牺牲一点召回率，换可控性。

**当前项目落点**：mini-agent 目前只有 session 内的 messages，跨 session 长期记忆是已知缺口，README 里写的是三层设计（会话内 messages / 跨会话摘要 / 单条事实记忆），代码只实现了第一层。

## 模块三 · Q2：用户要求"每天早上 9 点根据昨天聊天做复盘"，怎么设计

**结论**：拆成三件事——定时触发、原料从哪来、结果写到哪去。最容易做砸的是第二件。

**做法**

1. **触发用外部调度，不靠 agent 自己 sleep。** cron 每天 9:00 投一个任务进来，任务 id 用「用户 id + 日期」做幂等键，失败重试不会复盘两遍。
2. **原料用 trace，不是重新问模型"昨天聊了什么"。** mini-agent 的 trace 每轮都记了工具名、参数、结果摘要和耗时，复盘前先做一次确定性聚合：聊了几个话题、调了哪些工具、失败几次、哪一轮撞到最大轮次。聚合结果加关键对话再喂给模型写总结——这一步让复盘有事实依据，不是模型自由发挥。
3. **输出结构化。** 昨天完成的事、没完成的事、今天建议优先做的三件。落到待办工具和记忆里，而不是只发一条消息让人自己看。
4. **复盘结果写回记忆。** 第二天的复盘能读到前一天的结论，才不会每天重复同一句"你在准备面试"。

**取舍**：不让一个长驻 agent 自己算时间。长驻进程会被重启杀掉，状态也会漂移；定时交给外部调度最省心，agent 只负责被叫醒之后干活。另外复盘必须控长，超过 300 字用户就不看了，生成时直接限字数。

**当前项目落点**：trace 是现成的，复盘任务直接读 `logs/trace.jsonl` 就能还原当天发生了什么，不需要额外埋点。这也是我一开始坚持把每轮工具调用写成 jsonl 而不是只 print 的原因。

## 模块四 · Q2：session 处于 busy 时，新消息或异步工具完成事件到达怎么办

**结论**：把 session 当 actor 处理。同一个 session 永远只有一个执行者，所有输入进队列，只有队列消费端能改 state，从根上消掉并发写。

**做法**

1. **每个 session 一个 inbox 队列、一个执行协程。** busy 时新消息不打断当前执行，进队列，带优先级。
2. **消息分两类。** 普通追问排队等当前这轮跑完；带打断意图的（"停一下""别查了"）设 cancel 标志，在工具边界检查，当前工具返回后不再进下一轮，然后把队列里的新消息当成新任务起点。
3. **异步工具完成事件不要直接 append 成 role=tool 消息。** 这是最容易踩的坑：role=tool 必须紧跟对应 tool_call_id 的 assistant 消息，而异步完成的时机不可控，直接插进去消息序列就非法，下一次调用直接 400。
4. **正确做法是进 pending_events。** 在下一轮 LLM 调用之前把它合并成一条普通消息回注，例如"工具 search 已异步完成，结果如下：……"，再让模型继续。语义上模型照样能消费，序列上永远合法。

**取舍**：不做多线程共享 session state。锁粒度再细也会出现"工具结果写进了一个已经被压缩过的 messages 快照"这类问题。actor 串行化牺牲一点吞吐，换掉一整类竞态。

**当前项目落点**：现在是最朴素的单线程 repl，`input()` 阻塞期间天然串行，所以不存在 busy 冲突；要支持多端同时发消息，第一步就是加 inbox 队列。第 3 点那个坑我写 loop 时撞到过——assistant 的 tool_calls 消息必须先入 history，tool 消息才能跟上，顺序反了直接报错。

## 模块五 · Q1：Claude Code 的工具输出方式，和国内 GLM / 豆包的 OpenAI-compatible function calling 有什么不同

**结论**：这两者不是新旧关系，是两种取向。一个给模型宽原语加大量的上下文工程，一个给模型窄接口加强结构约束。

**差异在哪**

1. **工具粒度。** Claude Code 手里就那么几个宽工具（Bash、Read、Edit、Glob、Grep），大量能力靠模型自己拼 shell 命令，配合 prompt 里的工作规范。function calling 是一个个窄接口，每个带 JSON Schema，模型只能在给定参数空间里填。
2. **输出形态。** 前者工具结果以普通文本块回到对话里，模型自由解读，可以接着用、只用一部分、也可以忽略。后者是结构化的 tool_calls 配 tool_call_id，哪次调用、调用几次、结果对应哪一次，机器能精确追踪。
3. **扩展成本。** 前者加能力主要是改 prompt、写文档，一天能加好几个；后者每加一个工具就要设计一份 schema，工具多了 schema 本身吃掉大量 context，还得做动态加载。

**优缺点**：Claude Code 路线的优点是表达力和组合性近乎无限，模型能用 bash 做出你没想到的事，加能力极快；缺点是结果不可预期，权限和审计难做，出错恢复全靠模型自觉。function calling 的优点是强约束、参数可校验、支持并行调用、多模型可迁移（GLM、豆包、Qwen 都是同一套 schema）；缺点是僵化，参数差一个字段就废，工具一多上下文压力很大。

**取舍**：我的场景是业务系统集成，要的是可控和可迁移，所以选 OpenAI-compatible 路线。但 schema 的 description 我写得更口语，尽量让模型读到"这个工具是干嘛用的"，而不是只看到几个参数名。

**当前项目落点**：mini-agent 四个工具全走这套 schema，模型确实能自己组合出"先查天气再记待办"这种一次两调。如果工具涨到 20 个，我不会把 20 份 schema 全塞进去，会先按意图分组做动态加载。
