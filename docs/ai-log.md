# AI 使用记录（Prompt 与问题解决过程）

> 笔试要求"允许使用任何 AI 工具辅助开发"。这份记录保留的是**决策过程**，不是复制粘贴的代码：
> 每个模块我先问"为什么这么做"、拿到多个方案后自己选一个、写完再让 AI 挑错、跑测试验证。
> 代码是 AI 辅助产出的，但每个设计点的取舍理由我都能复述，见 README「系统设计」一节。

---

## 阶段 0：开工前的方向判断

**我的提问**
> 我要从零写一个最小可用 Agent，不能用 langgraph。请先告诉我：一个成熟 Agent runtime（Claude Code / OpenHands 这类）由哪些模块组成，哪些是"必须自己写"、哪些是可以省掉的？

**拿到的答案**
loop（决策-执行-回填）、工具注册表（schema 驱动）、会话状态、上下文管理、trace、异常兜底，这六块是骨架；流式、多 agent、沙箱、权限系统都可以省。

**我的决策**
先只写 loop + registry 两个文件，跑通再补其他四块。理由是：loop 是整个东西的地基，地基不对，后面全是返工。事实证明这个顺序省了很多时间——后面加 session、压缩、trace 都是往上叠，loop 一次没改结构。

## 阶段 1：核心循环与工具系统

### 记录 1：function calling 还是 ReAct 文本解析？

**我的提问**
> function calling 和让模型输出 Thought/Action/Observation 文本再由我正则解析，各自适合什么场景？我这个笔试题应该选哪个？

**AI 的回答要点**
function calling 有官方 JSON 约束、解析零成本、原生支持一次多调用；ReAct 文本格式对不支持 tools 的模型更通用，但解析要自己写，容错容易碎。

**我的决策**：主路径用 function calling（DeepSeek/Qwen 都支持），但解析层保留容错——`tool_calls` 不存在时按普通文本处理，`arguments` 是坏 JSON 时给空 dict 让校验层报错，不直接崩。

### 记录 2：工具参数错了，该 crash 还是喂回模型？

**我的提问**
> 模型给工具传了错参数（比如 todo 少了 content 字段），工程上更好的处理是什么？抛异常还是返回错误？

**AI 的回答要点**
把校验错误作为 tool result 喂回给模型，它会自己改参数或换工具重试。错误是模型能消费的信息，不是程序异常。

**我的决策**：`registry.execute()` 永不抛异常，统一返回字符串。校验失败返回 `参数校验失败: ...`，工具内部异常返回 `工具执行失败: ...`。这也是我认为"agent 工程"和普通 CRUD 最大的区别——错误要能被模型读懂。

### 记录 3：calculator 用 eval 还是 ast？

**我一开始的想法**：`eval(expression)` 三行搞定。

**AI 提醒**：`eval` 有注入风险，模型被诱导可以传 `__import__('os').system(...)`。

**我的决策**：改成 `ast.parse` + 节点白名单（只允许数字、四则、乘方、一元负号），其余直接拒绝。并补了注入用例测试。

## 阶段 2：会话与上下文

### 记录 4：session 存在内存还是落盘？

**我的判断**：题目说"用户可以随时接着窗口 1 继续聊"。如果只在内存里，进程重启就丢了，这条要求其实没满足。

**我的决策**：每个 session 一个 json 文件，`sessions/<session_id>.json`。多窗口靠 session_id 隔离，工具（todo）也从 session 拿数据，天然隔离。

### 记录 5：json 写一半崩了怎么办？

**我的提问**
> 直接 `open(...,'w')` 覆盖写 session，如果写一半进程被杀，文件会怎样？怎么避免？

**AI 的回答要点**
会留下半个 json，下次启动解析失败，整个窗口历史丢失。做法是写临时文件再 `os.replace` 原子替换（同盘是原子操作）。

**我的决策**：`save()` 写 `.tmp` 再 `os.replace`；`load()` 解析失败不抛异常，返回空 session 并打日志，保证程序能起来。

### 记录 6：压缩的阈值、保留窗口、触发点怎么定？

**我的提问**
> 200 轮对话的压缩应该在哪触发？保留多少条？阈值怎么估？

**讨论后的决策**
- 阈值 `3000 token`（可被 `AGENT_CONTEXT_MAX_TOKENS` 覆盖），中文按字、英文按 4 字符粗估。
- **触发点放在每轮 LLM 调用之前**，不是对话结束后。理由是：压缩的目的是"让下一次请求不超限"，放在请求前才是真正的守门人。
- 保留最近 6 条原文 + 前面全部折叠成一条摘要。system 消息永远保留（它是规则，不能被压缩掉）。
- 摘要用 LLM 生成，**失败时降级为规则拼接**，绝不因为压缩失败阻断对话。

### 记录 7：压缩摘要放 system 还是 user？

**我的提问**
> 生成的"[历史对话摘要]"应该以 system 角色插入，还是 user 角色？

**AI 的回答要点**
插 system 更"权威"，但会和主 system 抢权重，而且部分兼容实现不允许多条 system；插成 user 带标记兼容性最好。

**我的决策**：作为 `role=user` 带 `[历史对话摘要]` 标记插在 system 之后。实测 qwen 对这种方式理解稳定，压缩后追问"我的项目用了什么向量库"仍能答对 Chroma。

## 阶段 3：异常、trace、测试

### 记录 8：LLM 调用失败重试几次？哪些错误该重试？

**我的决策**：超时和 5xx 重试 2 次（指数退避），**4xx 不重试**。理由是 4xx 是请求本身有问题（key 错、参数错、余额不足），重试只会重复失败还烧钱。

### 记录 9：trace 记什么？

字段定为：时间、事件类型（llm_call / tool_call / context_compressed / max_iterations_reached）、工具名、入参、结果摘要、耗时 ms。原则是"能从日志复原一次完整执行"，但**不记 API key、不记完整 prompt**。

### 记录 10：测试怎么不依赖真实 key？

**我的决策**：写一个 `MockLLM`，按剧本返回预设的 `tool_calls` 或文本，把它注入 Agent。这样 24 个测试全部离线跑，2 秒出结果，也不会把 key 写进任何测试文件。真实链路另外用 `scripts/smoke_test.py` 单独验证。

## 阶段 4：真实调试过程（踩坑记录）

这几条是实际跑出来的问题，不是设计阶段想到的：

1. **测试红了 3 个**：
   - `test_tools.py` 里断言写错（把 `2**2` 的结果期望写成 `"4 = 4"`）——是我的笔误，改断言。
   - `test_invalid_args_fed_back_not_crash` 失败：初版校验只检查"必填字段存在"，没做更严格的类型校验，补了类型检查后通过。
   - 压缩降级路径对 `content=None` 的消息取首行时下标越界 → 加空值守卫，并让降级摘要带上工具名（否则压缩后模型不知道之前调过什么工具）。

2. **压缩在演示时"看不见"**：功能是对的，但面试演示时无法证明它发生了。于是加了两处可观测点——控制台打印 `🗜 触发压缩：10 条 → 8 条`，trace 里记 `event=context_compressed`。

3. **演示脚本重复运行会脏数据**：上一轮的待办还在 session 里，导致"窗口 2 看不到窗口 1 的待办"这一幕失真。改成开场自动清理 `demo-*` session。

4. **Windows 下 .env 加载**：不想为一个小功能引入 python-dotenv，手写了 20 行解析（跳过注释、支持 `KEY=VALUE`），并且**系统环境变量优先于 .env**，避免本地文件覆盖线上变量。

5. **`main.py` 从别的目录启动会 ModuleNotFoundError**：脚本里加 `sys.path` 兜底 + 在 README 写明"必须打开含 main.py 的那一层"，这其实是新手最容易卡住的地方。

## AI 使用的边界（自述）

- **我做决策，AI 做实现**：压缩时机、错误回喂、原子写、4xx 不重试这几个关键点，都是我提出问题、比较方案后拍板的；AI 给的是选项和理由。
- **每个"为什么"我都过了一遍**：README 的「系统设计」和这份记录里的每一条取舍，我都能脱稿讲出来——因为代码要进面试，讲不清就等于没写。
- **已知没做到的**：跨 session 的长期记忆、流式输出、工具并行执行。这三块我在 README 的"已知不足"里主动写了，并给了做法，没有假装实现。
