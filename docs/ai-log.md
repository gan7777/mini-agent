# AI 使用记录（Prompt 与问题解决过程）

> 笔试允许使用任何 AI 工具辅助开发，这里记的是**决策过程**，不是复制粘贴的代码。
> 我的实际做法是：先定边界（手写、不引框架、必须能量化演示），让 AI 出实现方案，
> 然后我判断方案合不合理、把它跑起来验证、并自己动手改了几处（见记录 11）。
> 每条取舍我都能顺着代码指到具体哪一行，README「系统设计」一节是结论版。

---

## 阶段 0：开工前的方向判断

**我的提问**
> 我要从零写一个最小可用 Agent，不能用 langgraph。先告诉我：一个成熟 Agent runtime（Claude Code / OpenHands 这类）由哪些模块组成，哪些必须自己写、哪些可以省掉？

**结论**
loop（决策-执行-回填）、工具注册表（schema 驱动）、会话状态、上下文管理、trace、异常兜底，这六块是骨架；流式、多 agent、沙箱、权限系统都可以省。

**取舍**
先只写 loop + registry 两个文件，跑通再补其他四块。loop 是地基，地基不对后面全是返工。事实证明这个顺序是对的：后面加 session、压缩、trace 都是往上叠，loop 的结构一次没动。

## 阶段 1：核心循环与工具系统

### 记录 1：function calling 还是 ReAct 文本解析？

**我的提问**
> function calling 和让模型输出 Thought/Action/Observation 再由我正则解析，各自适合什么场景？这个笔试题该选哪个？

**结论**
function calling 有 JSON 约束、解析零成本、原生支持一次多调用；ReAct 文本格式对不支持 tools 的模型更通用，但解析要自己写，容错容易碎。

**取舍**：主路径用 function calling（DeepSeek/Qwen 都支持），解析层保留容错——`tool_calls` 不存在就按普通文本处理，`arguments` 是坏 JSON 就给空 dict 交给校验层报错，不直接崩。

### 记录 2：工具参数错了，该 crash 还是喂回模型？

**我的提问**
> 模型给工具传了错参数（比如 todo 少了 content 字段），抛异常还是返回错误？

**结论**
把校验错误作为 tool result 喂回模型，它会自己改参数或换工具重试。错误是模型能消费的信息，不是程序异常。

**取舍**：`registry.execute()` 永不抛异常，统一返回字符串。校验失败返回 `参数校验失败: ...`，工具内部异常返回 `工具执行失败: ...`。我认为这是「agent 工程」和普通 CRUD 最大的区别——错误要能被模型读懂。测试 `test_invalid_args_fed_back_not_crash` 专门守这个行为。

### 记录 3：calculator 用 eval 还是 ast？

**我一开始的想法**：`eval(expression)` 三行搞定。

**问题**：`eval` 有注入风险，模型被诱导可以传 `__import__('os').system(...)`。

**取舍**：改成 `ast.parse` + 节点白名单（只允许数字、四则、取余、整除、乘方、一元负号），其余直接拒绝，并补注入用例。
**后续**：这个白名单后来被证明不够（记录 11）。

## 阶段 2：会话与上下文

### 记录 4：session 存在内存还是落盘？

**判断**：题目要求"用户可以随时接着窗口 1 继续聊"。只在内存里，进程一重启就丢，这条其实没满足。

**取舍**：每个 session 一个 json，`sessions/<session_id>.json`。多窗口靠 session_id 隔离，todo 也从 session 取数据，天然隔离。

### 记录 5：json 写一半崩了怎么办？

**我的提问**
> 直接 `open(...,'w')` 覆盖写 session，如果写一半进程被杀，文件会怎样？怎么避免？

**结论**
会留下半个 json，下次启动解析失败，整个窗口历史丢失。做法是写临时文件再 `os.replace` 原子替换。

**取舍**：`save()` 写 `.tmp` 再 `os.replace`；`load()` 解析失败不抛异常，返回空 session 并打日志，保证程序能起来。

### 记录 6：压缩的阈值、保留窗口、触发点怎么定？

**我的提问**
> 200 轮对话的压缩应该在哪触发？保留多少条？阈值怎么估？

**取舍**
- 阈值 `3000 token`（可被 `AGENT_CONTEXT_MAX_TOKENS` 覆盖），中文按字、英文按 4 字符粗估。
- **触发点放在每轮 LLM 调用之前**，不是对话结束后。压缩的目的是"让下一次请求不超限"，放在请求前才是真正的守门人。
- 保留最近 6 条原文 + 前面全部折叠成一条摘要。system 永远保留（它是规则，不能被压掉）。
- 摘要用 LLM 生成，**失败时降级为规则拼接**，绝不因为压缩失败阻断对话。

### 记录 7：压缩摘要放 system 还是 user？

**我的提问**
> 生成的"[历史对话摘要]"应该以 system 角色插入，还是 user 角色？

**结论**
插 system 更"权威"，但会和主 system 抢权重，而且部分兼容实现不允许多条 system；插成 user 带标记兼容性最好。

**取舍**：作为 `role=user` 带 `[历史对话摘要]` 标记插在 system 之后。实测 qwen 对这种放法理解稳定，压缩后追问"我的项目用了什么向量库"仍能答对 Chroma。

## 阶段 3：异常、trace、测试

### 记录 8：LLM 调用失败重试几次？哪些错误该重试？

**取舍**：超时和 5xx 重试 2 次（指数退避），**4xx 不重试**。4xx 是请求本身有问题（key 错、参数错、余额不足），重试只会重复失败还烧钱。

### 记录 9：trace 记什么？

字段：时间、事件类型（`llm_call` / `tool_call` / `context_compressed` / `max_iterations_reached`）、工具名、入参、结果摘要、耗时 ms。原则是"能从日志复原一次完整执行"，但**不记 API key、不记完整 prompt**。

### 记录 10：测试怎么不依赖真实 key？

**取舍**：写一个 `MockLLM`，按剧本返回预设的 `tool_calls` 或文本，注入 Agent。这样 26 个测试全部离线跑，2 秒出结果，也不会把 key 写进任何测试文件。真实链路另外用 `scripts/smoke_test.py` 单独验证。

### 记录 11：被追问「9**9**9 呢」，白名单挡不住算不完的表达式（我自己动手改的）

**怎么发现的**：演示 calculator 时被问"你这个 ast 白名单安全吗，那 `9**9**9` 会怎样"。我当时答不上来，回头实测——进程直接卡死，8 秒都算不完。`9**9**9` 不涉及任何代码注入，它能顺利通过白名单，但计算量是天文数字。

**结论**：ast 白名单解决的是"不能执行任意代码"，解决不了"合法输入把进程拖死"。工具是模型调用的，模型的输入不可预期，所以工具层必须自带规模上限，不能假设调用方是善意的。

**改了什么**（`agent/tools/calculator.py`）：
- `_safe_eval` 里对 `ast.Pow` 单独设闸：指数绝对值 > 100 直接拒绝；底数 > 1e6 且指数 > 1 也拒绝。其余算子不受影响。
- `_calc_handler` 加表达式长度上限 200 字符（防超长表达式拖慢解析）。
- 结果若溢出成 `inf` 返回错误，而不是把 `inf` 当答案。
- 补两条测试：`test_calculator_rejects_pow_bomb`（同时验证 `2**10 = 1024` 正常可用）、`test_calculator_rejects_overlong_expression`。测试数从 24 → 26。

**代价**：`2**200` 这类合法的大数运算现在会被拒。我接受这个取舍——面试题场景里没人需要用这个工具算 2 的 200 次方，但一次卡死会让整个对话不可用。

## 阶段 4：真实调试过程（踩坑记录）

这几条是实际跑出来的，不是设计阶段想到的：

1. **测试红了 3 个**：
   - `test_tools.py` 里断言写错（把 `2**2` 的结果期望写成 `"4 = 4"`）——笔误，改断言。
   - `test_invalid_args_fed_back_not_crash` 失败：初版校验只检查"必填字段存在"，没做类型校验，补了类型检查后通过。
   - 压缩降级路径对 `content=None` 的消息取首行时下标越界 → 加空值守卫，并让降级摘要带上工具名（否则压缩后模型不知道之前调过什么工具）。

2. **压缩在演示时"看不见"**：功能是对的，但无法证明它发生了。于是加两处可观测点——控制台打印 `🗜 触发压缩：10 条 → 8 条`，trace 里记 `event=context_compressed`。

3. **演示脚本重复运行会脏数据**：上一轮的待办还在 session 里，导致"窗口 2 看不到窗口 1 的待办"这一幕失真。改成开场自动清理 `demo-*` session。

4. **Windows 下 .env 加载**：不想为一个小功能引入 python-dotenv，手写了 20 行解析（跳过注释、支持 `KEY=VALUE`），并且**系统环境变量优先于 .env**，避免本地文件覆盖线上变量。

5. **`main.py` 从别的目录启动会 ModuleNotFoundError**：脚本里加 `sys.path` 兜底 + 在 README 写明"必须打开含 main.py 的那一层"，这是新手最容易卡住的地方。

## AI 使用的边界（自述）

- **我定边界和验收标准，AI 出实现**：六块骨架的范围、"必须能量化演示"、测试不依赖真实 key，这些是我定的；具体某个函数怎么写，AI 给的方案更多。
- **我负责验证和纠错**：每条取舍我都能指到具体文件和行号（比如压缩触发点在 `loop.py` 调 `context.maybe_compress` 的位置、错误回喂在 `registry.execute` 的 try/except），跑测试、跑 smoke_test、看 trace 都是我自己做的。
- **有一处是我自己动手改的**：记录 11 的幂运算上限——起因是被问住了，实测卡死，然后改代码补测试。
- **已知没做到的**：跨 session 的长期记忆、流式输出、工具并行执行。这三块在 README 里主动写了做法方向，没有假装实现。
